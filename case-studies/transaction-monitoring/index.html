Case 01 / Transaction monitoring

Functional prototype · Public synthetic demo

From uploaded payment signals to explainable investigation alerts.

A governed, file-based Streamlit workbench for demonstrating how payment activity can be validated, evaluated and organised for human investigation.

It is an early-stage analyst-support MVP—not a real-time decision engine, autonomous fraud blocker, certified scheme product or production case-management platform.

01 / Executive summary

A monitoring workbench built around explainability.

The project explores a practical question: how can a small risk team turn an uploaded transaction file into a reviewable monitoring run without hiding the reasoning inside a black box?

I designed and built the public MVP across the Python processing layer, governed rule configuration, Streamlit interface, analyst outputs, documentation and regression tests. The repository is public under the MIT licence, and the hosted application is intentionally limited to synthetic or fully anonymised demonstrations.

The demonstrated value is structural rather than a claimed business outcome: source rows are checked before evaluation, monitoring rules expose their purpose and thresholds, related hits become investigation alerts, and the analyst can trace an alert back to supporting evidence.

02 / Problem and users

A rule hit is not yet an investigation.

Transaction-monitoring work becomes difficult when data arrives in inconsistent files, rule settings vary by merchant or MID, and raw matches create workload without explaining what should be reviewed. A useful analyst tool must separate data-quality problems from risk indicators and monitoring signals from preventive limits.

Who the prototype is for

  • Transaction-monitoring analysts reviewing synthetic runs
  • Risk operations teams inspecting workload and concentration
  • Rule administrators comparing current and proposed settings
  • Reviewers who need an evidence trail behind an alert

What could go wrong

  • Incorrect column mapping can invalidate otherwise successful processing
  • Generic thresholds can overwhelm analysts with legitimate concentration
  • Missing history can prevent baseline scenarios from becoming eligible
  • Raw hits can be mistaken for confirmed fraud or AML findings
Monitoring, not prevention

The prototype records four configured acceptance-limit breaches as transaction context. Those limits do not create transaction-monitoring alerts and the application does not block payments.

03 / Solution architecture

A traceable route from file to review.

The architecture stays intentionally direct: one Streamlit interface orchestrates mapping and review, while the Python monitoring module handles validation, normalisation, configuration resolution, evaluation, alert consolidation, simulation and exports.

  1. Source: load a synthetic or fully anonymised CSV, XLS or XLSX file.
  2. Validate: confirm mappings, size, date, amount and critical-field usability.
  3. Resolve: apply global, plan, merchant, MID and valid temporary settings.
  4. Evaluate: run eligible monitoring scenarios and retain rule evidence.
  5. Consolidate: organise related hits into investigation alerts.
  6. Review: inspect alerts, merchant/MID behaviour, data quality and exports before tuning controls.
04 / Approach

Build the control around the analyst’s questions.

  1. 01
    Define the boundary

    Keep the public environment synthetic, batch-oriented and explicitly separate from real-time preventive decisions.

  2. 02
    Make data quality visible

    Validate the source before monitoring and connect missing fields to the scenarios they affect.

  3. 03
    Govern the rule logic

    Record purpose, eligibility, threshold logic, evidence, false-positive risks and analyst action for each scenario.

  4. 04
    Consolidate the story

    Preserve every raw hit while grouping related evidence into a smaller investigation queue.

  5. 05
    Support review and tuning

    Expose rule performance, merchant/MID context and current-versus-proposed simulation without calling concentration a measured false-positive rate.

Implemented monitoring layers

  • Velocity and decline: card approvals, declines and decline-to-approval sequences
  • Merchant and MID: static volume, deterministic baselines and observed dormancy
  • Identity linkage: email, phone and cross-merchant card-token relationships
  • Geography: payer/GeoIP mismatch and configurable country-list review
  • Patterns: exact repeated amount and refund/reversal-rate baseline signals
  • Governance: exact-match internal watchlists, rule inheritance and temporary overrides
05 / Decisions and trade-offs

Important choices stay visible.

Explainable rules before model complexity

Deterministic thresholds and trailing averages make the reason for a match inspectable. They are easier to govern, but they still require representative data and careful calibration.

File ingestion before API integration

CSV and spreadsheet input lowers the barrier to demonstration and analysis. The trade-off is batch processing, manual mapping and no direct gateway control.

Consolidated alerts without discarding hits

Grouping related evidence reduces the raw-hit workload while retaining the underlying transactions and scenario evidence for reproduction.

Human review over autonomous action

A match indicates where to look; it is not proof of fraud, money laundering or a policy breach. Decisions remain outside the prototype.

06 / Risk and compliance

The safe boundary is part of the design.

Controls demonstrated

  • Public-demo mode and explicit synthetic-data warnings
  • Upload size and row-count limits
  • Masked card evidence in alerts
  • Formula-injection neutralisation in spreadsheet exports
  • Bounded caching and a session clear control
  • Security and private-deployment guidance

Controls still required for operations

  • Authentication, authorisation and tenant isolation
  • Encrypted durable storage and retention controls
  • Persistent rule approvals and analyst dispositions
  • Secrets management, audit logs and incident response
  • Privacy review and production threshold governance

This case study describes a portfolio prototype and is not legal, regulatory or scheme-compliance advice.

07 / Implementation

A small stack with clear responsibilities.

Interface
Streamlit pages for run setup, alert review, merchant/MID behaviour, rule performance, simulation, reports and configuration.
Processing
Python and pandas for ingestion, normalisation, evaluation, scoring, consolidation, simulation and report preparation.
Configuration
PyYAML and a governed public-demo rule catalogue with synthetic entities and empty watchlists.
Exports
CSV, YAML, JSON and Excel outputs using openpyxl with spreadsheet-safe text handling.
Testing
pytest regression tests plus Streamlit application testing and a separate synthetic benchmark script.
Deployment
Public GitHub source and Streamlit Community Cloud, restricted by policy to synthetic or fully anonymised demonstrations.

What the tests establish

  • Every monitoring rule carries the required governance fields

  • Spreadsheet formula-like text is neutralised
09 / Limitations

What this prototype does not do.

  • No live transaction integration. Monitoring runs evaluate an uploaded file; they do not connect to or control a payment gateway.
  • No real-time blocking. Preventive acceptance controls are shown as context, not executed as payment decisions.
  • No production case workflow. Alert statuses and analyst dispositions are not persisted for multi-user review.
  • No persistent behavioural history. Linkage and baselines rely on history included in the current upload.
  • Important data remains absent. There is no stable customer ID, device fingerprint, source IP, chargeback linkage, authoritative MID lifecycle or original-refund link.
  • No currency conversion. Cross-currency amount aggregation can be misleading unless the input is already normalised.
  • Public demo data is synthetic. It cannot establish detection accuracy, false-positive performance or operational impact.
  • No certification claim. The project does not claim scheme certification or formal regulatory compliance.
10 / Current value

Demonstrated structure, not invented outcomes.

No production fraud-reduction, accuracy, revenue, workload or false-positive result is claimed. What the public prototype demonstrates is a foundation for clearer monitoring work:

  • Monitoring and preventive controls are separated explicitly
  • Rule purpose, evidence and effective scope remain inspectable
  • Data-quality gaps are connected to affected monitoring areas
  • Related hits can be reviewed as an investigation narrative
  • Merchant, MID and rule concentration can support calibration
  • Source, evidence and reports can be reproduced from one run
11 / Lessons and next iteration

The next evidence must come from controlled use.

The prototype reinforced that explainability depends as much on data quality and configuration provenance as on the scenario itself. Consolidation helps only when the analyst can still inspect the raw driver, while a behavioural baseline is useful only when its history is representative.

A credible next iteration would add persistent rule versions and dispositions, load de-duplicated prior history into evaluations, introduce stable customer/device/IP and chargeback fields, calibrate thresholds on approved representative data, and add the authentication, retention and audit controls required for private operational use.

Owner confirmation before production merge

Confirm the first-person role wording and continued publication approval for the repository and demo links.
